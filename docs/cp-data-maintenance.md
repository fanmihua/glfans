# 百家饭资料维护

本栏目整理公开的荧幕合作与演员履历，不推断私人关系。数据按演员去重维护，同一演员出现于多对 CP 时复用同一份资料。中、英、泰页面共用事实与链接。

## 数据入口

- `src/features/cp/actor-profiles.js`：GL Spotlight 公开演员目录核对的姓名、生日、身高和 INS/X，明确标记为二手目录。
- `src/features/cp/member-profiles.js`：既有艺人资料、第一方补充及来源优先级；经纪公司/本人事实优先于目录。生日只知道月日时保存 `birthdayMonthDay`，不补造年份。
- `src/features/cp/actor-socials.js`：微博和补充 X 账号、来源类型、核对日及冲突线索。优先使用已核对的微博 UID；只有公开昵称时使用 `/n/` 路由。不能把粉丝号当本人。
- `src/features/cp/cp-communities.js`：核对真实超话名后使用微博官方主题跳转；它是粉丝社区，不是官方 CP 账号。尚未确认直达地址时页面只提供明确标记的搜索入口。
- `cp-data.js` / `cp-expanded-data.js`：组合成员及共同作品；作品 ID 与考古档案、播出日历共用。
- `cp-timeline.js` / `cp-status.js`：个人里程碑、双人节点及明确官方合作结束通知；没有证据时为待核实，不能用总数减已结束数推算合作中。
- `cp-media.js` / `cp-children.js`：官方音乐、MV、影像以及「她们的娃」的归属和故事。娃不显示价格、库存或购买控制。

## 每轮流程

1. 阅读当前 AGENTS.md，检查已有未提交修改，保留与本轮无关内容。
2. 运行 `npm run stats:cp` 和 `npm run plan:cp`。覆盖率统计只读本地数据，不访问网络；检索仅处理 `output/cp-qa/maintenance-plan.json` 中的 `due`，按 `searchGroups` 合并同一演员的多个缺项，不能遍历全部资料重新搜索。
3. `npm run research:cp` 默认只生成到期计划，不发网络请求。只有初始化目录、明确新增演员或人工排查来源结构时才使用 `npm run research:cp -- --catalogue`；这条显式命令读取公开目录并缓存 30 天，候选不等于第一方确认，绝不直接覆盖资料。
4. 用艺人/经纪公司主页、本人链接页、制作方和播出平台优先核对。公开媒体或粉丝索引须保留真实来源类型，不包装为官方认证。遇登录、403、验证码或抓取失败，不绕过限制，不把失败等同账号不存在。
5. 新增资料逐条保留来源与核对日。生日/账号有冲突时保留已支持的事实，未知项为空；对缺项作明确待核实标记，不生成同名平台账号。不要保存私人联系方式、私人住址、未公开行程或粉丝猜测。
6. 姓名相似时按完整演员身份和官方演职员表核对。例如两位 Mim、两位 Atom、两位 Ice 必须区分；JanJingjing 不对应 ViewMim 的 Bake Love Feeling。演职员名单不能任意两两拼成 CP。
7. 双人合作结束须有明确官方双人公告；单方解约、换搭、粉丝站关闭或暂时沉默本身不足以判定。日期不确定的项目保留在 CP 页，不编入确定播出日历。
8. 数据写入后运行 `npm run build:cp`、`npm run test:cp`、`npm run stats:cp`、`npm run build`、`npm run test:sites`、`git diff --check`。`build:cp` 从正式资料生成每个 CP 的独立详情和轻量目录，并为原图生成带内容哈希的 WebP 尺寸档；不手改 generated 文件，不修改原图。有 UI 变化时在真实浏览器验收 321px 手机和桌面，以及中英泰切换。正文不得横向溢出，社交入口热区至少 44px。
9. 无事实变化不修改核对日期制造更新。只报告真实新增、更正或需处理的阻塞。来源统一放页面底部折叠区。

## 增量核对规则

- 已有姓名、生日、身高及已收录历史节点为稳定资料，默认不重复检索。星座由生日计算，不设搜索任务。有冲突或明确纠错线索时用 `--force target-id` 单独复核。
- 已确认 INS / X / 微博 / 超话每 90 天核对，不按周重搜。
- 新作品、待播/未定档项目、音乐/MV、未来活动和合作公告每 7 天查新增；已明确结束合作的组合降为 90 天新消息巡检，历史公告不重写。不用日期自动推断合作结束。
- 缺项从 14 天起退避：28、56、112，最高 180 天。每次只能记录真实检索，不能把“这一轮没搜”记成“没找到”。HTTP 错误不是缺项，7 天后重试；冲突保留原事实并提示处理。
- 持久化账本 `src/data/cp-maintenance-state.json` 保存字段指纹、上次尝试/核实日、缺项次数和证据。计划只读账本，不自动把到期任务变成已完成。字段实际变化、明确纠错均可触发复核。
- 研究完成后把本轮实际处理的结果写成 JSON 数组：`[{"id":"计划中的完整 id","outcome":"unchanged","sources":["https://官方来源"]}]`。`verified/unchanged` 必须有来源；`missing` 还需实际 `queries`；`error/conflict` 需 `note`。新事实先核对并改正式资料，然后记录成功；结果命令不修改事实。
- 先运行 `npm run plan:cp -- --record output/cp-qa/reviews.json` 预览，核对后加 `--apply` 更新账本。相同结果重复记录不累计次数；只记录本轮已处理的目标，未处理任务继续到期。账本变化不等于页面资料变化，不为纯账本变更重复部署网站或通知用户。

## 加载与弱网验收

`src/features/cp/generated/index.json` 只含目录/搜索必需信息；详情通过动态导入按 CP 加载，切换后复用模块缓存。档案与日历关联入口不能直接导入 `cp-data.js` 或演员资料。图片尺寸由浏览器依屏幕及像素密度选择，保持既有裁剪和排版。`scripts/preview-cp-network.mjs` 是本地测试服务器：150 ms 延迟、共享 200 KB/s、gzip、禁缓存；只注入测试计时，不进入正式构建。它不模拟手机 CPU，结果不可当作真实用户性能分位数。

## 本地与发布边界

现有 `glfans` 每周任务已扩展为「剧集日历与 CP 资料更新」，仍为每周一北京时间 10:00。保留日历原有的独立干净主线工作树和发布流程。用户已授权本轮 CP 功能在验收后整合最新主线并发布；这不改变后续定时任务的边界：CP 定时维护先做本地更新与验证，不能夹带开发分支或用户改动进入日历发布，未来定时自动发布须有明确授权。
